Lab case study

Application security hardening case study.

A secure software development project focused on identifying, exploiting, fixing and retesting weaknesses in an open-source hospital management system.

Overview

This project used a hospital management system as the baseline application and applied a structured hardening process across requirements, design, implementation and testing. The main goal was to reduce exploitable weaknesses without changing the core features of the application.

The system handled sensitive flows involving patients, doctors and admins, so the security work focused on authentication, authorization, input validation, session protection and configuration security.

What I worked on

  • Defining security requirements and mapping them to OWASP Top 10 and OWASP ASVS.
  • Analysing weaknesses in the baseline application and documenting exploitation paths.
  • Implementing security fixes and verifying that the original behaviour was no longer exploitable.
  • Supporting testing and evidence collection around the before-and-after state of the application.

Security issues addressed

The hardened version addressed stored XSS, insecure direct object reference in appointment cancellation, plaintext password storage, broken access control on admin pages, missing rate limiting on login forms and directory browsing exposure. Each issue was tested in the vulnerable version first and then retested after the fix.

The fixes included output encoding, ownership checks, password hashing and verification, stronger session validation, brute-force protection and Apache configuration changes to restrict directory listing and sensitive file access.

Testing approach

OWASP ZAP was used as the main security testing tool for scanning, fuzzing and checking application behaviour before and after hardening. Test cases focused on whether malicious inputs were safely handled and whether unauthorized users could still reach protected functionality.

This made the project feel less like a checklist and more like a real secure development cycle: identify the weakness, understand why it matters, implement a fix and prove that the original exploit path has been blocked.

Portfolio takeaway: this project shows practical web security work from both sides — understanding how flaws are exploited and then translating that into safer code, access control and configuration choices.

What I learned

The biggest lesson was that many high-impact web flaws come from trusting user input, trusting identifiers passed in URLs, or assuming that hiding a page is the same as protecting it. It also showed how much difference small code and configuration changes can make when they are tied to clear requirements and tested properly.
