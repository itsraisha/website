Lab case study

Open-source SOC with Wazuh, Suricata and Auditd.

A small AWS-based SOC designed to show how different data sources can be correlated into one readable attack timeline, from reconnaissance through brute force to post-exploitation activity.

Overview

I built this lab using a hive-sensor architecture on AWS EC2. The hive acted as the central Wazuh manager and dashboard, while the sensor acted as the monitored endpoint generating Suricata, authentication and Auditd logs that were forwarded for analysis.

To simulate an external attacker, I used Kali Linux in VirtualBox and ran a simple attack chain: Nmap reconnaissance, Hydra SSH brute force, successful login and post-compromise file activity. The main goal was not just to detect events, but to investigate them from the point of view of a SOC analyst.

What I tested

  • Network reconnaissance against the sensor using Nmap.
  • SSH brute force using Hydra to generate repeated authentication failures and one successful login.
  • Post-exploitation actions like file creation, permission changes and file deletion to mimic payload staging and cleanup.
  • Multi-source alert correlation across Suricata, SSH/PAM logs and Auditd.

How detection worked

Suricata gave visibility into the early network stage, especially scanning and suspicious SSH-related traffic, while authentication logs showed repeated failures followed by successful access. Auditd then captured what happened after compromise, including commands linked to file creation, chmod changes and deletion events.

I also created custom Wazuh rules to make key Auditd events easier to investigate in the dashboard. Those rules focused on file creation, permission changes and deletion so the post-exploitation sequence became much clearer during timeline reconstruction.

Key findings

The most useful lesson was seeing how each log source answers a different question. Suricata could show that the host was being targeted, authentication logs showed that access attempts were happening, and Auditd showed what was done on the host after access was gained.

That made the timeline much more convincing than any single alert on its own. It also showed why SOC investigation depends on correlation, not just severity levels or one noisy event stream.

Portfolio takeaway: this lab is less about “installing tools” and more about building an analyst workflow - detecting an attack chain, pivoting between data sources and explaining what happened clearly.

Challenges

One challenge was getting Auditd and Wazuh to work cleanly together so events were correctly collected, parsed and shown in the dashboard. Another was alert noise: some file-deletion-style events came from Wazuh’s own processes, which showed me that not every alert is malicious and tuning matters just as much as detection.

What I’d improve next

  1. Tighten Auditd scope so alerts focus more on relevant user directories and less on background system noise.
  2. Refine the custom rules to reduce repeated or overly broad matches.
  3. Add cleaner screenshots and diagrams showing the attack flow and alert timeline.
  4. Expand the lab with one more attacker technique so the investigation includes a wider range of post-compromise behaviour.
